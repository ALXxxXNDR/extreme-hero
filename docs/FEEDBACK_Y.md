## 0. 핵심 결정 5개

이 다섯 개가 나머지 전부를 지배한다. 뒤집으려면 여기부터 뒤집는다.

### 결정 ① 과열을 **「칸당 실행 2회 상한」**으로 갈아끼운다

과열은 확률 감쇠·피해 보너스·RELOAD 페널티·HUD 온도계·잔열까지 다섯 가지를 겸하던 물건이었다.
그 자리를 **딱 하나의 규칙**이 대신한다.

> **"한 칸은 한 바퀴에 두 번까지만 밟습니다."**

종료성이 **확률이 아니라 산수로** 증명된다(스텝 ≤ 2 × 칸수 = 10). 유저가 한 문장으로 이해한다.
흐름 각인의 보상은 "한 번 더 때린다" 그 자체이고, 비용은 "쉬는 시간(RELOAD)이 늘어난다"이다.
상세는 §1.

### 결정 ② 각인은 **칸 10종 + 레일 5종 = 15종**으로 전면 교체한다

기존 24종 중 **10종만 이름·문구를 갈아 승계**하고 14종은 폐기, **레일 각인 5종을 신설**한다.
칸/레일 구분이 세공사 3택(피드백 ⑨)의 구조를 만들고, 동시에 **레일 각인은 "어느 칸에?" 2단계를
건너뛴다** — 피드백 ②가 지적한 그 화면을 반쯤 없애 버린다. 상세는 §2.

### 결정 ③ 속성은 **한자를 버리고 색을 다시 배정한다** — 7계는 유지

`불 · 얼음 · 번개 · 독 · 기름 · 타격 · 정신`.
「초(超)」와 「유(油)」가 사라진다. 겹치던 보라 두 개(기름·정신)를 **기름 = 갈색**으로 갈라놓고
불을 주황에서 **빨강**으로 옮긴다. 7계를 줄이지 않는 이유는 §3에 근거와 함께 적었다.

### 결정 ④ 스킬 아이콘은 28장을 새로 그리지 않는다 — **실루엣 14 × 속성색 7**

`불 + 장판` / `독 + 큰베기`처럼 **속성색(배경) × 동작 실루엣(전경)** 조합으로 읽힌다.
28장 고유 그림을 그리는 대신 **14개 픽토그램 한 장**만 구우면 되고, 같은 속성 안에서
실루엣이 겹치지 않도록 데이터 검사로 못 박는다(§4.4). 에셋 비용이 절반 이하로 떨어지고
"알아보기 쉽게"라는 요구를 구조적으로 만족한다.

### 결정 ⑤ 난이도는 **HP를 내리고 물량·패턴을 올린다** — 그리고 저장은 **schema 4**

HP 곡선 세 축을 전부 내리고(§5.5) 물량·정예·습성 패턴을 올린다.
각인 24종 폐기 + 레일 각인 신설 + 발견 상태 저장 때문에 **schema 3 세이브는 열 수 없다.**
정직하게 **schema 4로 올리고 v3 세이브를 폐기한다**(v1·v2 폐기 선례를 따른다).

## 1. (A) 과열 제거 후의 루프 종료성

### 1.1 지금 무엇이 무엇을 막고 있었나

`scripts/core/rune_engine.gd`의 안전망은 넷이다.

| 층 | 상수 | 실제로 하던 일 |
|---|---|---|
| ① 확률 상한 | `P_CAP = 0.75` | 확정 발동 금지 |
| ② **과열 감쇠** | `HEAT_DECAY = 0.62` (`p_eff = p × 0.62^load`) | **유일한 확률 감쇠** |
| ③ 스텝 상한 | `STEP_CAP = 14` | **종료 자체는 여기가 이미 보장하고 있었다** |
| ④ 하드 가드 | `HARD_LOOP_GUARD = 112` | 엔진 버그 탐지용 |

**중요한 사실**: 종료성은 원래도 ②가 아니라 ③이 보장했다. ②가 한 일은 "STEP_CAP에 닿는 빈도를
0.70%까지 낮추는 것"과 "긴 사이클을 경제적으로 손해로 만드는 것"이었다
(`reload = 빚 × (1 + 과열 × 0.18)`이 초선형이라 오래 도는 것이 손해였다).

그러므로 과열을 빼면 **터지는 것은 종료성이 아니라 경제성**이다.
빚만 남으면 `reload`가 스텝 수에 **선형**이고, 사이클 시간도 선형이므로
DPS = Σ피해 / (Σ지속 + Σ빚)가 길이에 거의 무감각해진다 → "제일 센 칸을 무한히 되밟는 것"이 정답이 된다.
**따라서 대체 규칙은 확률 감쇠가 아니라 하드 바운드여야 한다.**

### 1.2 새 규칙: 칸당 실행 2회 상한

```
SLOT_EXEC_CAP := 2      # 새 상수. rune_engine.gd 상단
```

세 줄로 끝난다.

1. 바늘이 **이미 두 번 밟은 칸**에는 다시 들어가지 않는다. 진행 방향으로 **건너뛴다.**
2. 진행 방향에 밟을 수 있는 칸이 남아 있지 않으면 **그 바퀴가 끝난다**(`end_reason = "all_used"`).
3. 상한에 걸린 칸으로 보내려는 각인은 **굴리지도 않는다**(발동 낭비가 눈에 보이면 안 된다).

### 1.3 종료성 증명

**정리.** `simulate_cycle()`은 최대 `2n` 스텝(칸 5개 → **10스텝**)에 반드시 종료한다.

**증명.** `E = Σᵢ executed[i]`라 두자.
- 메인 루프 한 바퀴는 `executed[cursor]`를 정확히 1 올린다(`link` 동시 실행이 있으면 다른 칸도 1 더 오른다).
  따라서 **E는 매 반복마다 최소 1 증가한다.**
- 이동 단계는 `executed[j] < SLOT_EXEC_CAP`인 칸으로만 커서를 보내고, 그런 칸이 없으면 종료한다.
  따라서 **모든 i에 대해 항상 `executed[i] ≤ 2`이다.**
- 그러므로 `E ≤ 2n`이고, E가 매 반복 최소 1 오르므로 **반복 횟수 ≤ 2n**. ∎

건너뛰기 스캔은 진행 방향으로 최대 n칸을 훑고 없으면 종료하므로 O(n)이고,
전체는 O(2n²) = 50연산이다. 확률·시드와 무관하게 성립한다.

**따라서 `STEP_CAP`은 게임 규칙이 아니라 방어 단언이 된다.**
`STEP_CAP := 2 * SLOT_COUNT + 2 = 12`로 낮추고, `end_reason == "overload"`는
**몬테카를로에서 0건**이어야 한다(그것이 새 회귀 계약이다 — 기존 "과부하율 0.70%"를 대체).

### 1.4 과열이 하던 일의 재배치

| 과열이 하던 것 | 어디로 갔나 |
|---|---|
| 확률 감쇠 `0.62^load` | **칸당 실행 2회 상한**(하드 바운드 10스텝) |
| 피해 보너스 `+12%/스택` | **삭제.** 흐름의 보상은 "한 번 더 때린다" 자체다 |
| RELOAD 페널티 `×(1+0.18H)` | **빚 선형 누적만 남긴다** — 밟은 칸 수에 비례. `reload = 빚 × reload_scale` |
| 과부하 → RELOAD 6초 벌칙 | **삭제.** 상한이 규칙이 됐으므로 도달은 벌칙이 아니다. `RELOAD_CAP 6.0`은 유지 |
| 재진입 감쇠 `0.82^n` | **삭제(1.0).** "두 번 발동한다"가 약속인데 두 번째가 약하면 거짓말이 된다 |

| `heat_gate`(열기) 각인 | 폐기 |
| `overcharge` L1 반응(불→번개 · 과열 +1) | **의미 교체** — "이 칸이 붙이는 상태의 세기 ×1.3"(기존 `potency` 채널 재사용, 새 코드 0) |
| 결속 `BOND_FIRE_COST`(과열 반값) | **결속 폐기.** 과열이 없으면 정의 자체가 없다. 자리는 레일 각인 `rail_color`가 산다 |
| 삼각(1·3·5 같은 형태 · RELOAD −12%) | **폐기.** 형태를 화면에서 지우므로(피드백 ⑬) 계획할 수 없는 규칙이 된다. `rail_rest`가 대신한다 |
| 공명(인접 같은 원소 +15%) | **유지.** 색이 나란히 보이므로 유일하게 눈으로 계획할 수 있는 배치 규칙이다 |
| **마왕 반격 창 = RELOAD** | **유지.** 과열 없이도 성립한다(빚만 본다). 다만 §1.6의 재보정이 필요하다 |

`form`(참격/관통/파동/설치/수호) **데이터는 남긴다** — 저장·아이콘·미래 대비.
`FORMS` 배열과 `form_counts()`는 그대로 두고 **게임 규칙 소비자만 0으로 만든다.**

### 1.5 새 규칙이 만드는 경제

한 칸을 두 번 밟으면 **피해 2배 · 빚 2배 · 지속 2배**다. 그래서:

- 되밟을 가치가 있는 칸 = **피해 ÷ (지속 + 빚)이 덱 평균보다 높은 칸**.
  예: `execution` 4.20/(1.62+0.77) = 1.76 vs `meteor_blade` 2.45/(1.95+0.98) = 0.84.
  **"제일 좋은 칸에 앙코르를 붙여라"** 가 한 줄로 성립하는 진짜 선택이 된다.
- 최대 이득은 **정확히 2배로 묶여 있다.** 폭주가 구조적으로 불가능하다.
- 흐름 각인은 여전히 **확률**이라 변동성이 비용이다(실시간 액션에서 회피 타이밍을 못 짠다).
- 각인 자리가 유한하다(칸 총 5 · 같은 id 3 · 과밀 감쇠) — 흐름은 피해 각인과 자리를 다툰다.

### 1.6 반드시 함께 재보정할 것 (Y8 웨이브)

| 축 | 왜 | 어디 | **Y8 실측 결과** |
|---|---|---|---|

> ### ⚠️ 「스테이지 보스도 같은 이유」는 틀렸다 — Y8 실측
> 재보정 근거로 적은 이유는 "칸당 실행 2회 상한 때문에 한 바퀴의 빚이 최대 2배가 된다"인데,
> **앙코르를 만드는 것은 흐름 각인뿐이고 스테이지 보스는 각인이 0개다**(부록 A-2 ⑫).
> 그래서 보스의 빚은 패턴 `reload`의 **고정 합**이고 시드와 무관하다 —
> `balance_probe` ⑨의 「빚평균 = 빚최대」가 그 증거다. 빚이 2배로 벌어질 수 있는 것은
> 각인을 `BOSS_RUNE_CAP`(16)개까지 갖는 **마왕뿐**이다.
>
> 재보정의 진짜 근거는 **창 길이 자체**였다. 0.75 / 0.55에서 여섯 변종의 창은
> `A 1.24 · B 1.35 · C 1.10 | A+ 1.34 · B+ 1.43 · C+ 1.25`로 셋이 1.3초 아래였다.
> 1.1초짜리 창으로는 스테이지 보스의 존재 이유("RELOAD에 때린다"를 가르친다)가 안 선다.
> 0.90 / 0.60에서 `A 1.49 · B 1.62 · C 1.31 | A+ 1.46 · B+ 1.56 · C+ 1.37` — 여섯 전부 창 안이다.
>
> **최종 수치는 언제나 `GameTuning`·`BossLibrary`가 정본이다.** 이 표는 근거이지 값이 아니다.

### 2.2 표 — 레일 각인 5종

레일 각인은 **칸이 아니라 레일 전체**가 소유한다. 칸을 교환해도 따라가지 않고, 붙일 칸을 고르지 않는다.

### 2.6 세공사 가격과의 연결

기존 가격식을 **그대로 쓴다.** 항 하나만 갈아끼운다.

```
값 = (희귀도 기본가 + 18 × 구매횟수) × 흐름 1.25 × 확정 1.15 × 굴림(0.85~1.15) × 상점가 스케일
```

- 희귀도 기본가 45 / 80 / 135 **유지**.
- `RUNE_SHOP_FLOW_PREMIUM(1.25)`의 대상: `twice` `back_one` `jump_one` `trade_skip` `rail_loop` `finisher`.
- `RUNE_SHOP_PASSIVE_PREMIUM(1.15)`의 근거 문구가 "과열을 한 톨도 안 올린다"였다 →
  **"굴리지 않고 항상 켜져 있다"**로 근거를 다시 쓴다. 값은 유지.
- **레일 각인 할증 신설** `RUNE_SHOP_RAIL_PREMIUM = 1.20` — 칸을 고르지 않고 즉시 붙으며
  칸 교환·카드 이동에 흔들리지 않는다. 편의에 값을 매긴다.

정규 사다리 총액이 X1 실측 752~1,049 G였다. 레일 할증으로 약 +6% 오른다 → **재측정 대상**.

## 3. (C) 속성 재작명과 색 재배정

### 3.1 7계 유지 판정 — **유지한다**

줄이자는 유혹이 있지만 세 근거로 유지한다.

1. **28장 = 7 × 4가 데이터·아이콘 좌표에 박혀 있다.** `element_counts()`가 원소당 정확히 4장을
   단언하고 아이콘 아틀라스도 7×4 = 28칸이다. 계를 줄이면 카드 재배치 + 아틀라스 + `data_test`가
   함께 무너진다 — 이번 라운드에서 가장 비싼 변경이 될 것이고 유저가 요구한 것도 아니다.
2. **"생산자 5 + 소비자 2" 구조가 §4 콤보 언어의 골격이다.** 5개가 상태를 만들고 2개가 거둔다.
   여기서 하나를 빼면 "쌓는다 → 터뜨린다" 문장이 성립하지 않는 원소가 생긴다.
3. **유저의 불만은 개수가 아니라 이름과 색이었다.** ("초가 무슨 말인지 모름 / 화·초 색 구별 안 감")

### 4.2 카드 설명의 새 형식 — **한 문장이 아니라 두 짧은 줄**

지금은 `desc` 한 줄이 동작·횟수·넉백·사거리를 전부 나른다(X1이 그렇게 만들었다).

| 필드 | 내용 | 길이 상한 | 색 |
|---|---|---|---|
| `desc` | 무엇을 하는가 (횟수 포함) | **16자** | 본문색 |
| `combo` | 무엇과 어울리는가 | **18자** | **속성색** |

### 4.5 "두 배로 쌓는다"의 구현 (⚠️ 밸런스 파급)

`cross_cut`의 `combo`가 유저가 직접 예시로 든 문장이다. 실제로 작동하게 하려면:

```gdscript
# status_engine.gd _row_poison()
var add: float = maxf(1.0, float(ctx.get("stack_bonus", 1.0)))
state[F_POISON_STACKS] = minf(state[F_POISON_STACKS] + add, POISON_STACK_MAX)
```
`combat_resolver`가 카드의 `status_stack_bonus` 키를 `ctx`로 넘긴다. **`cross_cut` 한 장만 2.0.**

> ⚠️ **이것은 `card_status_power()` 축을 여는 것과 같은 범주다.** AGENTS.md §12가
> "지금 축을 넣으면 V10이 확정한 보스 HP 표가 무효가 된다"고 명시한 그 축이다.
> 다만 **카드 1장 · 독 한 갈래로 한정**하므로 파급이 측정 가능하다.
> Y8이 `balance_probe` ⑫를 다시 돌린다. 한(chill) 강화 계수는 **여전히 열지 않는다.**

### 5.5 난이도 = 패턴·물량 (피드백 ⑰)

**내린다 — HP 세 축**

| 축 | 지금 | 새 값 | 근거 |
|---|---|---|---|
| `MonsterLibrary.CYCLE_HEALTH_GAIN` | 0.24 | ~~0.16~~ → **0.21**(Y8 확정) | §9.5가 예고한 2차 조정. 최상위 hellhound 682 → ~~560~~ **617** HP |
| `STAGE_HP_BASE` | 1.00/1.55/2.10/2.65/3.20 | **1.00/1.35/1.70/2.05/2.40** | 5스테이지 −25% |
| dwell HP `H(d)` | `1 + 0.14d + 0.012d²` | ~~`1 + 0.10d + 0.007d²`~~ → **`1 + 0.13d + 0.010d²`**(Y8 확정) | d=12에서 ×4.41 → ~~×2.2~~ **×4.00** |

> ### ⚠️ 이 표의 산수 오류 2건 — Y1이 발견하고 Y8이 정정했다
>
> ```
> hellhound @ power_level 13.6   (= 16.0 × slash_hits 10 × (1 + gain × 13.6))
>   0.24 → 682 HP    ← 위 표의 682 맞음
>   0.16 → 508 HP    ← 위 표는 560이라 적었다. 0.16으로는 560이 안 나온다
>   0.21 → 617 HP    ← Y8 확정값
>
> dwell H(12) = 1 + 12a + 144b
>   0.14 / 0.012 → 4.408   ← 위 표의 ×4.4 맞음
>   0.10 / 0.007 → 3.208   ← 위 표는 ×2.2라 적었다. 2차항을 빠뜨린 숫자다(1 + 0.10×12 = 2.2)
>   0.13 / 0.010 → 4.000   ← Y8 확정값
> ```
>
> ### ⚠️ 그리고 더 큰 문제 — **세 축이 곱해진다**
>
> 위 표의 세 줄은 각각 −25% 안팎으로 읽히지만 몹 체력에는 **곱해서** 실린다.
> Y1이 넣은 값(0.16 / 2.40 / 0.10·0.007)의 실측 복리는 런에서 실제로 지나는
> 다섯 자리의 기하평균으로 **−42%**였고, 5스테이지·dwell 12·power 13.6이라는 극단
> 좌표에서는 **−59%**였다. 의도는 −25%다.
> Y8이 `scripts/test/balance_probe.gd` ③으로 그 곱을 자리마다 재고 **−25.8%**로 맞췄다.
> 되돌리거나 다시 만질 때도 **세 축을 한꺼번에** 봐야 한다. 한 축만 올리면 곡선이 뒤틀린다.
>
> ### ⚠️ dwell 축은 난이도가 아니라 **체류 압박**의 축이다
>
> `H(d)`를 내리면 킬당 효율(`H^-0.5`)이 완만해져 §6.2가 못 박은 "d=12에서 시간을 두 배"가
> 깨진다. Y1의 0.10/0.007에서는 **×1.79**였다(실측). Y8이 0.13/0.010으로 올려 **×2.000**을
> 회복했고, HP 총량을 맞추는 몫은 `CYCLE_HEALTH_GAIN` 쪽이 진다.
>
> **최종 수치는 언제나 `core/tuning.gd`(`GameTuning`)·`monster_library.gd`·
> `boss_library.gd`가 정본이다.** 이 문서의 숫자는 그 값을 **유도한 근거**이고,
> 둘이 어긋나면 코드가 맞다 — 위 정정 3건이 그 실례다.

> 체류 압박의 실체(킬당 효율 = XP× / HP×)는 지수비가 정하므로 곡선을 완만히 해도
> **압박의 방향은 유지된다** — 다만 절대 수입이 줄어 레벨 진행이 느려진다.
> `balance_probe` ⑧⑩⑪을 다시 돌리고 필요하면 몹의 `xp` 기본값을 +1씩 올린다.

## 6. (F) 발견 기반 내비 · 랜덤 이벤트 · 재미 아이템

### 6.1 발견 규칙 — **안개는 쓰지 않는다**

X3가 "필드가 보이는 면적 96.7%"를 만들었다. 그 위에 안개를 씌우면 정면으로 되돌린다.
**발견은 화살표의 유무로만 표현한다.**

| 항목 | 규칙 |
|---|---|
| 상태 | 오브젝트마다 `discovered: bool`. 스테이지 스코프 |
| 발견 조건 | 플레이어와의 거리 ≤ **520px** 이거나 **화면 안에 들어옴**(`NAV_RING` 안쪽) |
| 발견 전 | EdgeMarker **없음.** 오브젝트 자체는 시야에 들어오면 당연히 보인다 |
| 발견 후 | EdgeMarker 영구 표시(그 스테이지 동안) |
| 성·캠프 | **처음부터 발견 상태**로 시작한다. 정비 창구를 못 찾으면 게임이 막힌다 |
| 보스문·균열·이벤트 | 발견 전에는 화살표 없음 |
| 저장 | 새 키 `discovered_features: Array[String]` (→ schema 4) |

> ⚠️ **길잡이 스텝 ⑥이 "가장자리 화살표"를 가리킨다.** 발견 기반이 되면 그 시점에
> 화살표가 하나도 없을 수 있다. → **스텝 ⑥을 "성 쪽으로 걸어가 화살표를 켜 보라"로 다시 쓴다.**
> 성이 처음부터 발견 상태이므로 화살표는 항상 있다. `--guide-test aim`이 이 스텝을 검사한다.

### 6.2 랜덤 이벤트

배치는 균열과 같은 규약이다 — **스테이지 시드로 결정적**, 스테이지당 2~3개,
`dwell 0`에 1개 · `dwell 2` · `dwell 4`에 각 1개. 런 최대 12개.

| 이벤트 | 최소 스테이지 | 내용 | 보상(× 스테이지 스케일) |
|---|---|---|---|
| **작은 던전** | 1 | 입구 `E` → 정예 3파도 → 탈출 | 골드 ×1.6 + 각인 3택1 |
| **보물섬** | 2 | 호수 가운데 섬 · 다리 1개 | 상자 3개 확정(함정 없음) |
| **세미 엘리트** | 2 | 이름 있는 중형 1기(HP ×4 · 패턴 2종) | 장비 2택1 + 골드 |
| **유랑 상인** | 1 | 필드 임시 상점(1회) | 카드 1 + 장비 1 (성보다 20% 비싸다) |
| **무너진 사당** | 3 | 체력 절반을 바치고 각인 1개 | 각인 3택1 |
| **마왕의 발자국** | 잠식 중 | 전조 2기 동시 | 각인 뜯기 2회 |
| **굶주린 무리** | 1 · 밤 | 같은 종 8기가 몰려온다 | XP ×2.2 |
| **별똥별** | 1 · 밤 | 낙하 지점에 상자 | 상자 1 + 재미 아이템 1 |

난이도 스케일: 정예 수 `3 + stage`, HP는 스테이지 배율 그대로.
보상은 골드·XP가 상점가 스케일(`1 + 0.35 × (스테이지−1)`)을 탄다.

구현 재사용: 균열(`world_grid.spawn_rift_near`)의 배치·예산·저장 구조를 그대로 복제한다.
**새 `state`를 만들지 않는다** — 전부 `playing` 안의 필드 사건이다(보스방·균열 선례).

### 6.3 재미 아이템 — **소비형** 8종

**판단: 소비형이다.** 장비형으로 만들면 4부위 경쟁에 들어가 "재미"가 아니라 "빌드 결정"이 되고,
피드백 ⑫가 요구한 부위별 비교 플로우를 더 복잡하게 만든다.

조작: **소비 슬롯 1칸 + `Q` 키.** 이미 들고 있는데 새로 주우면 **바꿀지 묻는다**
(피드백 ⑫의 장비 교체 확인과 **같은 UI 컴포넌트를 쓴다** — 만드는 김에 두 곳에서 쓴다).

| 아이템 | 효과 | 획득처 |
|---|---|---|
| **낡은 지도** | 이 스테이지 오브젝트를 **전부 발견** 처리 | 상자 · 던전 |
| **해시계** | 지금 낮을 **40초 늘린다** | 상자 · 상인 |

| **회복의 빵** | 체력 **40% 회복** | **상자**(피드백 ㉓) |
| **되돌이 종** | 성으로 **즉시 귀환** | 상인 |
| **각인 지우개** | 칸 하나의 각인을 전부 떼고 **골드로 되판다** | 세공사 |

「낡은 지도」가 유저가 말한 "맵 전체 밝혀 내비 활성화"의 이 게임식 표현이다 —
안개를 만들지 않고도 같은 쾌감을 준다.

### 6.4 보물상자 재배당 (피드백 ㉓)

| 칸 | 지금 | 초안(합 106 · 틀림) | **확정** |
|---|---|---|---|

| 각인 드래프트 | 14 | 14 | **14** |
| **체력 회복** | — | **7** (신설 · 체력 40%) | **7** |

> ### ⚠️ 초안 열의 합은 100이 아니라 **106**이었다 — Y6이 발견하고 Y8이 정정했다
> `14+13+16+15+14+7+6+6+7+5+3 = 106`. 신설 두 칸(체력 7 · 재미 6)을 더하면서

> `chest_slice_for()`를 부르며, `--event-test`의 `chest` 묶음이 합 100과 위협 18을 문다.

위협 총량 21% → **18%**로 낮춘다. 상자가 "열면 손해일 수도"라는 인상을 주면
발견 기반 내비의 동기가 약해진다.

## 7. (G) 타격감

### 7.1 원칙 세 줄

1. **카메라는 거의 움직이지 않는다.** 화면 흔들림은 **진폭 ≤ 4px · 지속 ≤ 0.12초**,
   그리고 **보스 착탄과 플레이어 피격에만** 쓴다. **플레이어 스킬 발사에는 흔들림 0.**
2. 타격감은 **대상 쪽**에서 만든다 — 피격 플래시 · 경직 · 넉백 · 파편 · 숫자.
3. 히트스톱은 **대상만** 세운다. 프레임 전체를 세우지 않는다
   (X4의 `world_running` 동결과 개념이 충돌하고, 78기 환경에서 위험하다).
   구현은 이미 있는 `hit_stun_timer`를 그대로 쓴다.

### 7.2 몹별 피격 반응 프로필

`MonsterLibrary.MONSTERS`에 세 키를 추가한다 — `kb_sens`(넉백 감수성) · `stun_sens`(경직) · `slow_sens`(둔화).
`enemy.gd:744 apply_hit_reaction()`의 `resistance`에 곱한다(새 순회 0).

| 몹 | 무게 | kb | stun | slow | 피격 연출 |

| 이끼콩 | 가벼움 | 1.6 | 1.4 | 1.3 | 튕겨 날아가며 이끼 파편 |
| 들멧돼지 | 무거움 | 0.5 | 0.7 | 0.8 | 버티며 흙먼지. **돌진 중이면 넉백 0** |
| 뿔임프 | 보통 | 1.1 | 1.0 | 1.0 | 뒤로 구른다 |

### 7.3 스킬별 충격 프로필

`deal_card_library.knockback_profile()`은 지금 `kind` 하나로 넉백을 유도한다.
카드마다 authored `impact` 키를 추가하고 그 키가 우선한다.

| impact | 넉백 | 경직 | 시간 효과 | 쓰는 카드 |
|---|---|---|---|---|
| `push` | 강 | 짧 | — | cleave · lion_roar · meteor_blade |
| `pin` | 0 | **김** | 대상 정지 0.25초 | execution · thrust |
| `slow` | 약 | 짧 | 이동 −35% 1.2초 | frost_ring · dash_blade |
| `drag` | 끌어당김 | — | — | gravity_well |
| `rush` | 중 | 중 | **점점 느려짐**(0.9 → 0.5, 1.5초) | aura · sword_rain |
| `haste_self` | — | — | **내 이동 +20% 0.8초** | time_cut · phantom_step |
| `stagger` | 약 | 김 | 대상의 공격을 취소 | shield_bash · rapid_slash |
| `pop` | 위로 튕김 | 중 | 0.3초 공중(이동 불가) | holy_pulse · earth_splitter |

"점점 느려짐"은 새 자원을 만들지 않는다 — 기존 `cycle_slow_multiplier` / `cycle_slow_timer`에
`cycle_slow_ramp: bool` 하나를 얹어, 켜져 있으면 타이머가 흐를수록 배율이 0.9 → 0.5로 내려간다.
`_physics_process`의 기존 타이머 블록 한 줄이다.

"빨라짐"(`haste_self`)은 플레이어 쪽이므로 `player.gd`에 짧은 부스트 타이머 하나.

### 7.4 카메라 최소화의 검증

`--cycle-test`에 계측을 신설한다 — 12초 전투 동안 **카메라 오프셋의 최댓값**을 기록하고
`cam_peak ≤ 4.0`을 단언한다. 설정의 「화면 흔들림」을 0으로 두면 `cam_peak == 0.0`이어야 한다.

| ⑧ | **필드 토스트 마왕 초상** | `_build_boss_growth_toast` `game.gd:7864`의 `PORTRAIT_SCRIPT.new()`(검은 사각형 + 뿔, `pixel_portrait.gd`)를 **`art/v2/boss-demon-king.png`**(원본 `Actor/Boss/GiantRedSamurai` — **이미 구워져 있다**)의 Idle 0프레임 `TextureRect`로 교체. 자리 `(10,18) 74×104` 무변경. `pixel_portrait.gd`는 프로젝트에 남은 **유일한 무한 애니메이션**(`sin(elapsed*8.0)` 상시 점멸)이므로 이 교체로 그것도 함께 사라진다 |

## 12. 추측 구간 (확인하지 못한 것)

정직하게 적는다. 아래는 **읽어서 확인한 사실이 아니라 계산·추론**이다.

1. **§1.6의 재보정 값 전부**(`BOSS_RELOAD_MUL` 0.42 등)는 산수로만 잡았다. `balance_probe` 실측이 아니다.
2. **§5.5의 HP·물량 신값 6개**도 마찬가지다. 특히 `CYCLE_HEALTH_GAIN 0.16`은
   `monster_library.gd`가 예고한 조정 방향을 따랐을 뿐 새로 측정하지 않았다.
3. `current_enemy_limit()`이 `MAX_ENEMIES 78`로 클램프되는지 **코드로 확인하지 않았다.**
   Y5·Y8이 먼저 확인해야 한다.
4. **§8 ㉔의 결과 화면 원인**은 코드 구조(PARCHMENT 껍데기 + SLATE 칩 + 밝은 글자)로 추론한 것이고
   **실제 깨진 스크린샷을 보지 않았다.** 세로 겹침은 계산상 없다(레일 300~450 ⊂ 274~452).
   유저가 본 "겹침"이 다른 원인일 수 있다 — Y4는 `--capture-result` **승리 컷**부터 찍어 확인할 것
   (지금은 패배 컷만 찍는다고 AGENTS.md §12가 적어 뒀다).
5. **§3.2의 색 분리**는 색상환 각도와 명도로 판단했고 실제 렌더(안개 0.24 + 비네트 0.55 + 알파 0.34 덧칠)에서
   확인하지 않았다. 5스테이지 밤 캡처가 유일한 판정 수단이다.
6. **§4.3의 28장 문구**는 초안이다. 16자/18자 상한 안에서 더 나은 표현이 있을 수 있고,
   YZ의 한글 스윕이 다시 손댈 것을 전제한다.
7. `--capture-choice`가 카드 두 장을 뽑을 때 `combo` 줄이 늘어난 만큼 **카드 높이가 모자랄지**
   계산하지 않았다. Y4가 기하를 먼저 잰다.
8. **레일 각인의 저장·복원이 마왕에게도 필요한지** 판단하지 않았다.
   마왕은 플레이어와 같은 런타임을 쓰므로(정체성 #12) 원칙적으로 필요하지만,
   `DemonLord.sync_runes()`가 칸 단위로만 기록한다. Y2가 "마왕은 레일 각인을 갖지 않는다"로
   좁히는 것이 안전하다 — 그러면 마왕 레일이 항상 5스텝이라 반격 창 계산도 단순해진다.
