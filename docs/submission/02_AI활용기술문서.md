### 1.2 한 문장 요약

> **게임 코드는 AI가 100% 작성했고, 인간은 콘셉트·제약·판단 기준을 정하고
> 실제 플레이 화면을 보며 방향을 교정했다. AI는 자기가 짠 코드를
> 자기가 만든 자동 검사로 검증한 뒤 인간에게 올렸다.**

인간 디렉터는 GDScript를 한 줄도 타이핑하지 않았다. 대신 다음 네 가지를 했다.

1. **무엇을 만들 것인가**를 정한다 (콘셉트·차별화 축·게임의 정체성)
2. **무엇을 하면 안 되는가**를 정한다 (저작권 안전선, 어휘 금지어, 화면 점유 상한)
3. **실제 창을 띄워 플레이**하고 난이도·가독성·재미를 판단한다
4. **AI가 제출한 검증 결과를 승인하거나 반려**한다

### 1.4 사용한 AI 도구

| 도구 | 용도 | 산출물이 최종 빌드에 들어가는가 |
|---|---|---|
| **Claude Code** (Anthropic · 에이전트형 코딩 CLI) | **주 개발 에이전트** — 설계·구현·테스트·디버깅 전 영역. 추론 모델은 **Claude Opus 계열** | **예** — 게임 코드 전량 |
| **OpenAI Codex CLI** | **교차 검증·보조 구현** — 주 에이전트 산출물의 코드 리뷰와 대안 진단 | **일부** — 리뷰 지적을 반영한 수정과 보조 구현분 |
| **OpenAI 이미지 생성** | 비주얼 방향 참고용 콘셉트 시트 **1장** | **아니오** — 방향 참고용, 런타임 미사용 |
| **Godot 4.7.1 headless** | AI가 작성한 자동 검증 테스트의 실행기 (`--headless` 모드) | 검증 도구 (빌드 산출물 아님) |

**도구를 둘로 나눈 이유**는 단순하다. 코드를 쓴 모델과 그 코드를 의심하는 모델을
같은 것으로 두면, 같은 가정에서 나온 실수는 끝까지 발견되지 않는다.
그래서 **작성은 Claude Code가 전담하고, 위험한 구간(밸런스 상수·전투 판정·저장 스키마)은
Codex CLI에 다시 읽혀 두 번째 의견을 받는 방식**을 썼다. Codex는 보조 역할이며,
게임의 설계·구현·검증 본류는 Claude Code가 담당했다.

- 런타임 그래픽은 **Godot Draw API로 그린 오리지널 도형 + CC0 픽셀 에셋**이다.
- 사운드는 `AudioStreamWAV` 샘플을 **런타임에서 합성**한다.
- 외부 상용 게임 에셋은 **0건**이다.

## 2. AI와 인간의 역할 분담

아래 표가 이 프로젝트의 협업 계약이다.
**"AI가 만들고 인간이 고른다"**가 아니라, **"인간이 경계를 긋고 AI가 그 안을 채운 뒤
스스로 검증하고, 인간이 화면으로 최종 판정한다"**에 가깝다.

| 영역 | AI가 한 일 | 인간 디렉터가 한 일 |
|---|---|---|
| **콘셉트** | 장르 조합·선택 시스템 후보 다수 제안 | **"고르지 않은 것이 전부 마왕에게 간다"**는 인과 구조 확정 |
| **장르** | Phaser·Unity·Godot 비교, 구현 난이도·차별화 방식 분석 | 탑다운 액션 로그라이크로 확정, **뱀서류와의 차이를 직접 규정** |
| **엔진** | 세 엔진의 장단점 표 작성 | **Godot 최종 선택** |
| **전투 코어** | 5칸 딜싸이클 · 바늘 런타임 · 각인 15종 엔진 · 상태이상 5종과 반응 8쌍 구현 | 동시 발동 폐기 지시, **"한 칸만 나간다"** 규칙 확정, 과열 시스템 폐기 지시 |
| **월드 생성** | 무한 좌표 청크(Simple Tiled WFC) · 호수 · 바위 · 다리 · 랜드마크 3종 | **"바위와 물은 플레이어도 마물도 못 지난다"** 등 통행 규칙 확정 |
| **필드 생태** | 습성 5종(무리·겁쟁이·텃세·매복·사냥) · 지형 가중 스폰 · 돌 우회 AI | **"1·2스테이지 낮에는 아무도 먼저 덤비지 않는다"** 규칙 지시 |
| **성장 시스템** | 카드 2택1 · 취소 선택지 · 각인 드래프트 · 보스 트로피 5종 · 마왕 자동 합성 | 버린 것의 **귀속 범위**(스킬→장비→각인 조각)를 단계적으로 확장 지시 |
| **시각·UI** | UI 킷 10장, 픽셀 아이콘 생성 코드, 프레임리스 HUD, 호버 툴팁 컴포넌트 | **"블록을 다 지워라"·"중학생이 3초 안에 알아보게"** 같은 판정 기준 제시 |
| **사운드** | `AudioStreamWAV` 런타임 합성 효과음 | 톤·볼륨을 실제 플레이에서 판단 |
| **테스트** | headless 기능 검사 16종 · 캡처 15종 · 밸런스 프로브 5종을 **AI가 직접 설계·구현** | 통과 기준 승인, 캡처 육안 검수, **"이건 통과했는데 재미가 없다"** 판정 |
| **밸런싱** | `balance_probe.gd`로 DPS·TTK·골드 수지·체류 압박 정량 측정 후 상수 조정 | 목표 창(관문 30~60초 · 마왕 60~120초 · 15~20일 클리어) 확정 |
| **문서화** | 핸드오프 문서 36개 · 설계 문서 · 변경 로그 자동 작성 | 문서 체계 자체를 요구 (AI 세션이 끊겨도 이어지도록) |

여기서 "AI"는 대부분 **주 개발 에이전트인 Claude Code**를 가리킨다.
**OpenAI Codex CLI**는 그 옆에 **두 번째 눈**으로만 세웠다 — 밸런스 상수처럼 되돌리기
비싼 구간이나 원인이 안 잡히는 버그에서, 주 에이전트가 낸 코드와 진단을 그대로 넘겨
**다른 모델의 리뷰와 대안 가설**을 받는 용도다. Codex의 지적은 그대로 반영하지 않고
**인간 디렉터가 채택 여부를 판정한 뒤 주 에이전트에게 되돌려** 반영·재검증하게 했다.

## 3. 개발 워크플로우 — 이 프로젝트의 방법론

AI를 "코드 생성기"로 쓰면 1주짜리 게임잼에서 이 볼륨이 나오지 않는다.
다음 **네 가지 장치**가 실제로 속도를 만들었다.

### 3.1 세션 단위 개발 + 핸드오프 문서 체계

AI 에이전트 세션은 컨텍스트가 유한하고, 세션이 끝나면 기억이 사라진다.
그래서 **작업을 "웨이브(wave)" 단위로 쪼개고, 웨이브가 끝날 때마다
다음 AI 세션이 읽을 인수인계 문서를 AI가 직접 작성**하게 했다.

```
AGENTS.md  ← 단일 인수인계 원본(Single Source of Truth). 모든 세션이 먼저 읽는다
   └ docs/handoff-*.md  ← 웨이브별 상세 인수인계 36개
```

| 시리즈 | 문서 | 무엇을 한 라운드인가 |
|---|---|---|
| **W1~W11** | `handoff-w*.md` | v2 — 딜싸이클 레일 전투의 초기 구축 |
| **V1~V10** | `handoff-v*.md` | v3 — 5스테이지 개편 · 상태이상 · 보스 3종 · 트로피 · 저장 schema 3 |
| **U1~U3** | `handoff-u*.md` | UI 킷 전면 재스킨 + 스포트라이트 온보딩 길잡이 |
| **X1~X4** | `handoff-x*.md` | **1차 플레이테스트 피드백** — 레벨업 모달 · 편집 화면 · HUD · 온보딩 |
| **Y1~Y8, YA, YZ** | `handoff-y*.md` | **2차 플레이테스트 피드백 25건** — 과열 폐기 · 각인 15종 · 필드 생태 · 타격감 · 밸런스 실측 |

각 핸드오프 문서는 형식이 고정돼 있다.

| 절 | 내용 |
|---|---|
| **0. 한 문장** | 이 웨이브가 무엇을 바꿨는지 한 문장 |
| **1. 검증 결과** | 이 웨이브가 **직접 실행한** 검사와 그 출력 원문 |
| **2~N. 처리표** | 요구사항 → 구현 → 값 변경 대조표 |
| **밟은 함정** | 다음 세션이 같은 곳에 빠지지 않도록 남기는 경고 |
| **이 웨이브가 하지 않은 것** | 범위 밖으로 명시적으로 밀어낸 항목 |

특히 **「밟은 함정」 절이 핵심**이다. 예를 들어 `handoff-y5.md` §5-5는
"`enemy.gd`에 남은 디버그 `print`가 `=false` 문자열을 찍으면
`run_all.sh`가 통째로 FAIL이 된다"는 사실을 기록해 두었다.
이 한 줄 덕분에 이후 세션이 같은 원인으로 헤매지 않았다.

AI가 남기는 문서 규격도 `AGENTS.md` §14에 못 박아 두었다.

```markdown
- 사용자 요청:
- 상태: completed | in_progress | blocked | ready_for_playtest
- 결정한 내용:
- 변경 파일: `path/to/file`: 무엇을 변경했는지
- 사용자에게 보이는 변화:
- 데이터/저장 호환성:
- 실행한 검증: `정확한 명령` → PASS/FAIL/미실행
- 남은 문제:
- 다음 AI가 시작할 정확한 지점:
```

> 나쁜 기록의 예시까지 문서에 박아 두었다 — *"UI 수정함. 테스트 대충 됨. 다음에 계속."*
> 이런 문장이 나오면 인수인계 실패로 본다.

### 3.2 자동 검증 우선 — AI가 만든 코드를 AI가 만든 테스트로 검증

인간이 매번 게임을 켜서 확인하는 것은 1주 일정에서 불가능하다.
그래서 **AI가 기능을 만들 때 그 기능을 무는 headless 검사를 같이 만들도록** 했다.

```bash
bash godot-game/scripts/test/run_all.sh      # 컴파일 1 + 기능 검사 16종 (약 135초)
```

- 종료 코드 **0이면 전부 통과**. CI와 다른 AI 세션은 이 숫자만 보면 된다.
- 하나라도 아래에 걸리면 FAIL로 집계한다.
  ① Godot 종료 코드 ≠ 0 ② 기대한 `*_TEST_COMPLETE` 줄이 없음
  ③ 출력에 `=false`가 있음 ④ 출력에 `SCRIPT ERROR` / `ERROR:`가 있음
- 검사 항목: 월드 · **필드 생태** · 5칸 덱 · 성/트로피 · 균열 · 스트레스 · 스모크 ·
  전투 · 스테이지 클럭 · 상태이상 · 사이클 런타임 · 각인 드래프트 · 보스 3종과 마왕전 ·
  이어하기 · 길잡이 · **필드 사건**

밸런스는 별도 프로브가 **숫자로** 회귀를 막는다.

```bash
godot --headless --path godot-game -s res://scripts/test/balance_probe.gd   # 약 90초
```

`balance_probe`는 12개 절로 나뉘어 화력·몹 HP 복리 지수·체류 곡선·물량 상한·
경제·보스 TTK·마왕 TTK를 재고, 마지막 줄에 **`pass=1`**을 찍는다.
`AGENTS.md`는 **"밸런스 숫자를 바꾸기 전에 먼저 돌린다"**를 규칙으로 못 박아 두었다.

### 3.3 인간은 "실제 창"으로 판단한다

headless 검사는 **"무너지지 않았다"**를 증명하지만
**"재미있다 · 읽힌다 · 어렵다"**는 증명하지 못한다. 그 축은 전부 인간이 맡았다.

- AI가 `--captures` 모드로 실제 창을 띄워 **15종 73컷**의 PNG를 저장한다.
- 인간이 그 컷을 열어 보고 판정한다. 판정 기준도 문서에 문장으로 남긴다.
  - 편집 화면: **"중학생 3초 테스트"** — 처음 보는 사람이 컷 1장만 보고
    ①5칸이 순서대로 돈다 ②카드를 끌어 넣는다 ③각인이 칸에 붙어 있다 를 알아차리는가
  - HUD: **필수 검수 컷은 `hud-x3-stage5-night.png`** — 가장 어두운 화면에서
    체력 바·바늘·화살표·숫자가 전부 읽히면 나머지는 자동이다
  - 온보딩: **"한 페이지를 3초 안에 훑을 수 있는가"**
- 인간이 직접 플레이한 뒤 피드백을 문서로 넘긴다.
  2차 라운드는 **피드백 25건**을 `docs/FEEDBACK_Y.md`로 정리했고,
  그 문서의 §11이 **"25건 전부 배정됐다. 누락 0."**으로 추적을 닫았다.

### 3.4 정성적 판단도 검사 계약으로 바꿨다

가장 특이한 장치는 **"읽기 힘들다"는 감각을 숫자 계약으로 번역**한 것이다.

| 감각적 요구 | 코드가 매 실행 찍는 지표 | 계약 |
|---|---|---|
| "HUD가 필드를 가린다" | `hud_block_pct` / `hud_ink_pct` | 31.74% → **3.35%** |
| "편집 화면에 글이 너무 많다" | `edit_labels` / `edit_prose` | 상시 문장 라벨 **0건** · 글자 라벨 32개 이하 |
| "온보딩이 길다" | `onb_peak` / `onb_longest` | 페이지 ≤360자 · 한 줄 ≤32자 · 규칙 ≤2줄 |

한 번 숫자가 되면 **회귀가 자동으로 잡힌다.** 다음 세션이 설명을 한 줄 늘리는 순간
검사가 빨간불을 켠다. 이것이 "AI가 만든 UI가 세션마다 조금씩 다시 복잡해지는" 문제의
구조적 해법이었다.

## 4. 대표 디렉팅·교정 사례

각 사례는 **① 인간 디렉팅 → ② AI 구현 → ③ 검증** 3단으로 압축했다.

### 사례 1. 벽돌깨기로 새던 프로젝트를 '버린 선택의 귀환'으로 되돌리다

- **문제**: 흔한 뱀서라이크를 피하려던 AI가 게임을 **벽돌깨기**로 바꿔 버렸다.
- **인간 디렉팅**: *"장르를 바꿔서 차별화하는 게 아니다. **고르지 않은 선택이
  마왕에게 돌아온다**는 인과가 차별화다."*
- **AI 구현**: Godot 기반 탑다운 액션으로 전면 재구현. 버린 스킬 → 버린 장비 →
  버린 각인 조각까지 귀속 범위를 세 번에 걸쳐 확장.
- **검증**: `--smoke-test` → `state=won skills=4 rejections=4 boss_items=1`
- **의미**: **게임의 정체성은 AI가 결정하지 못했다.** 이 한 번의 교정이 나머지 전부를 낳았다.

### 사례 2. 뱀서류 재정의 — "몬스터는 낮에 필드에 살고 있어야 한다"

- **문제**: AI 초안은 화면 가장자리에서 적이 무한 생성돼 플레이어를 추격하는 구조였다.
- **인간 디렉팅**: *"낮에는 몬스터가 필드에 상주하고, 플레이어가 찾아가야 한다."*
  이후 2차 피드백에서 *"초원엔 약한 몹이 무리지어 배회"*, *"1·2스테이지 낮에는
  먼저 덤비지 않게"*로 구체화.
- **AI 구현**: 습성 5종(무리·겁쟁이·텃세·매복·사냥)을 기존 행동 AI 위에
  **직교 축**으로 얹고, 지형이 종을 정하는 가중 스폰과 돌 우회 경로를 구현.
- **검증**: `--field-test` 신설 → `habit_wired` · `habit_day` · `day_aggro_zero` ·
  `terrain_spawn` · `herd_spawn` · `rock_detour` 전부 true.

### 사례 3. 동시 발동 폐기 → 딜싸이클 레일로 전환 (게임의 중심 규칙 교체)

- **문제**: 스킬이 쿨타임마다 동시에 터지니 **플레이어가 무엇을 하고 있는지 안 보였다.**
- **인간 디렉팅**: *"동시 발동 구조를 폐기하고, 왼쪽에서 오른쪽으로 실행되는
  카드 공장으로 바꿔라. 빈칸은 기본 공격이고, 공격 도중 방향만 회전하며 타이머는 유지된다."*
- **AI 구현**: 카드 데이터 · 레일 런타임 · 지속시간과 RELOAD 분리 ·
  지속형 근접 히트 윈도우와 타격 ID 기록(중복 타격 방지)을 구현.
  이후 5칸 고정 + 각인 15종 + 속성 콤보 구조로 성숙.
- **검증**: `--cycle-test`(바늘 런타임) · `--v4-test`(5칸 덱) · 실제 1280×720 UI 확인.
- **의미**: 게임 제목이 `THE UNCHOSEN` → `딜싸이클 용사`로 바뀐 지점이 여기다.

### 사례 4. 과열 시스템 폐기 — "확률이 아니라 산수로 증명해라"

- **문제**: 각인이 바늘을 되돌려 한 바퀴가 무한히 길어지는 것을 **확률 감쇠**로 막고 있었다.
  플레이어는 왜 안 터지는지 이해할 수 없었다.
- **인간 디렉팅**: *"과열을 전면 제거해라."*
- **AI 구현**: 단 하나의 규칙으로 교체 — **"한 칸은 한 바퀴에 두 번까지만 밟는다."**
  그리고 종료성을 **수학적으로 증명**해 문서에 남겼다
  (`E = Σ executed[i]`가 매 반복 최소 1 증가하고 각 칸이 2를 못 넘으므로 **≤ 2n = 10스텝**).
- **검증**: `rune_test.gd` 몬테카를로 **25,001 사이클**에서
  `no_overload=true overload_count=0` — 상한 초과 0건.
- **의미**: AI가 규칙을 **구현**만 한 게 아니라 **성질을 증명**해 회귀 계약으로 바꿨다.

### 사례 5. 밸런스 교정 — 무조작 12초 사망에서 생존으로

- **문제**: 첫 자동 전투 테스트에서 **움직이지 않은 검사가 낮 12초 안에 사망**했다.
- **AI 분석**: 방향 공격 로직은 정상. 원인은 **낮 추적형 몬스터 비율 25%**.
- **AI 구현**: 낮 생성 확률을 도주 36% / 반격 32% / 무리 23% / 추적 9%로 재배분.
- **검증**: `--combat-test` → 12초 실제 물리·AI 실행 후에도 `state=playing`.
- **후속**: 이 축은 이후 `balance_probe`의 **체류(dwell) 압박 곡선**으로 정식화됐다.

### 사례 6. "블록을 전부 지워라" — 감각적 요구를 면적 숫자로

- **인간 디렉팅**: *"모든 정보들이 블록으로 나뉘어져 있어. 블록을 제거하고 다시 디자인해줘."*
  *"위치 알려주는 편의성은 아예 섹터를 지우고, 화면에서 화살표로 작게 navigation."*
  *"딜싸이클 범위가 너무 커 — 최대한 아이콘으로 미니모드."*
- **AI 구현**: 상시 9-slice 판 5장 → **0장**. 나침반 패널 삭제 → 화면 테두리를 도는
  `EdgeMarker` 4개. 딜싸이클 스트립 1048×156 → **380×74**(면적 15.1%),
  칸당 텍스트 25줄 → **0줄**.
- **검증**: 캡처가 매 실행 로그에 찍는 `HUD_COVERAGE block_pct`가
  **31.74% → 3.35%**(잉크 기준 3.7배 감소). 이후 이 값이 회귀 지표가 됐다.

### 사례 7. 버그 — 상자를 열면 상자 위치가 사라졌다

- **증상**: 보물상자를 연 뒤 상호작용 사전을 비우자, **같은 사전을 참조하던
  상자 좌표까지 함께 사라졌다**(참조 공유 문제).
- **AI 수정**: 상자 ID와 위치를 **먼저 값으로 복사한 뒤** 상호작용 상태를 비우도록 변경.
- **검증**: 상자 → 성 → 장비 배치/버리기 → 밤 전환 통합 테스트 통과
  (`--systems-test` 계열 → 현재 `--castle-test` / `--event-test`가 승계).

### 사례 8. 버그 — **검증 도구 자체가 틀린 것을 재고 있었다**

- **증상**: 밸런스 수치가 계속 어긋났다. 원인은 게임이 아니라 **`balance_probe`**였다.
  프로브의 덱 표가 **폐기된 구 각인 ID**를 쓰고 있어 `attach_rune()`이 조용히 실패했고,
  **레일 각인은 한 번도 주입되지 않았다.** 결과적으로 **각인 0개짜리 덱**을 재고 있었다.
- **AI가 스스로 찾은 지문**: 어느 행에서나 `steps`가 정확히 `5.00`이었다는 점 —
  흐름 각인이 0개일 때만 나오는 값이다.
- **AI 수정**: `balance_probe.gd` 전면 재작성(12절 · 판정 8축). 5스테이지 표준 덱의
  `raw_dps`가 **119.7 → 394.3**으로 바뀌었고, 보스 HP·마왕 HP·체류 곡선을 **전량 재측정**.
- **검증**: `BALANCE_PROBE_COMPLETE pass=1` (8축 전부 1) · **2회 연속 재현** ·
  `run_all.sh` 17행 전부 PASS 2회 연속.
- **의미**: **자동 검증에도 검증이 필요하다.** "테스트가 초록불"이 아니라
  "테스트가 **무엇을 재고 있는가**"를 의심하는 것이 AI 협업의 핵심 능력이었다.

### 사례 9. 함정 — 디버그 `print` 한 줄이 전체 검사를 빨갛게 만들다

- **증상**: `run_all.sh`는 출력에 `=false`가 있으면 FAIL로 집계한다.
  `enemy.gd`에 남아 있던 `print("Y5BLOCK … detouring=%s")`가 정확히 그 문자열을 찍었다.
- **AI 수정**: 디버그 `print` 제거, 관측은 변수(`last_herd_stood` / `last_herd_wanted`)로 이전.
- **기록**: 이 사실을 `handoff-y5.md` 「밟은 함정」에 남겨 **다음 세션의 재발을 차단**.

## 5. 대표 프롬프트

§4가 **"무엇을 고쳤는가"**라면, 이 절은 **"그것을 어떤 문장으로 시켰는가"**다.

이 프로젝트에서 프롬프트는 "요청문"이 아니라 **작업 지시서**에 가까웠다.
1주 안에 이 볼륨이 나온 이유의 절반은, 프롬프트마다 아래 네 가지를 **처음부터 같이 준** 데 있다.

| 구성 | 무엇을 적는가 | 없으면 생기는 일 |
|---|---|---|
| **① 목표** | 이 작업이 무엇을 만드는가 | AI가 인접한 더 쉬운 문제를 대신 푼다 |
| **② 제약·금지선** | 바꾸면 안 되는 것, 되돌아가면 안 되는 구조 | 매 세션 조금씩 원래대로 돌아온다 |
| **③ 상한·가드** | 규칙의 수치 상한과 밸런스 안전장치 | 무한 루프와 몰빵 조합이 나중에 터진다 |
| **④ 완료 판정** | 무엇이 초록불이어야 "끝"인가 | "된 것 같다"를 사람이 매번 확인해야 한다 |

> 아래 여덟 개 프롬프트는 실제 개발에서 내린 디렉팅을 **제출용으로 정제한 것**이다.
> 근거가 된 원문 디렉팅과 그 구현 대조표는 `docs/handoff-*.md` 36개 문서에
> **"사용자 원문 → 구현" 표**로 그대로 남아 있다.

### 5.1 프롬프트 1 — 게임의 정체성을 못 박다

**상황**: 뱀서라이크를 피하려던 AI가 게임을 **벽돌깨기**로 바꿔 놓은 시점.

```text
너는 이 게임의 구현 담당이고, 장르와 차별화 축은 내가 정한다.

[목표] 흔한 뱀서라이크와 다른 게임을 만든다. 단, 차별화 수단은 "장르 변경"이 아니다.

[확정 규칙 — 이건 바꾸지 마라]
  1. 장르는 탑다운 실시간 액션 로그라이크로 고정한다.
     벽돌깨기·퍼즐·리듬 같은 다른 장르로 갈아타지 마라.
  2. 차별화 축은 단 하나다 — "플레이어가 고르지 않은 선택은 전부 마왕이 가져간다."
     레벨업에서 버린 스킬, 교체하며 버린 장비가 그대로 최종 보스의 힘이 된다.
  3. 그래서 플레이어의 성장과 마왕의 강함은 같은 자원에서 나온다.
     이 인과가 끊기는 설계는 전부 반려한다.

[해야 할 일] 위 규칙 셋을 만족하는 최소 실행 버전을 Godot으로 다시 짜라.

[완료 판정] 한 판을 자동으로 끝까지 돌리는 검사를 함께 만들고,
  "버린 개수"와 "마왕이 받은 개수"가 일치하는지를 그 검사가 출력으로 단언해라.
```

**AI가 수행한 것**: Godot 기반 탑다운 액션으로 전면 재구현. 귀속 범위를 버린 스킬 →
버린 장비 → 버린 각인 조각까지 세 번에 걸쳐 확장했고, 한 판 전체를 자동으로 도는
`--smoke-test`를 함께 만들었다.

**결과·검증**: `--smoke-test` → `state=won skills=4 rejections=4 boss_items=1`.
이후 만들어진 모든 시스템(트로피·각인·마왕 자동 합성)이 이 규칙 위에 얹혔다.

### 5.2 프롬프트 2 — 중심 규칙 교체: 동시 발동 폐기 → 5칸 딜싸이클 레일

**상황**: 스킬이 쿨타임마다 각자 터지니 플레이어가 **자기가 뭘 하고 있는지 볼 수 없었다.**

```text
지금 전투는 "스킬이 쿨타임마다 각자 터지는" 구조다. 이 구조를 폐기하고 아래로 바꿔라.

[바꿀 것] 스킬을 칸에 꽂는 레일 하나로 만든다.
  - 바늘이 1번 칸부터 오른쪽으로 한 칸씩 이동하며 그 칸의 카드를 실행한다.
  - 마지막 칸을 넘어가면 한 바퀴가 끝나고, RELOAD 시간을 지불한 뒤 다시 1번 칸으로 간다.
  - 빈 칸은 기본 공격이다. 공격이 나가는 도중에는 방향만 회전하고 타이머는 유지된다.

[유지할 것] 기존 카드·아이템 데이터와 저장 파일은 최대한 살려라. 새로 만들 이유가 없다.

[불변식] "지금 무엇이 나가고 있는가"가 화면에서 항상 한 곳으로 읽혀야 한다.
  여러 개가 동시에 터지는 구조로는 어떤 이유로도 되돌아가지 마라.

[완료 판정]
  - 바늘 런타임을 실시간으로 도는 headless 검사를 만들고, 한 바퀴의 실행 순서·
    지속시간·RELOAD 길이를 출력으로 남겨라.
  - 지속형 근접 공격이 같은 적을 한 바퀴에 두 번 때리지 않는지 함께 단언해라.
  - 실제 1280×720 창은 내가 직접 띄워 최종 판정한다.
```

**AI가 수행한 것**: 카드 데이터 · 레일 런타임 · 지속시간과 RELOAD 분리 · 지속형 근접
히트 윈도우와 **타격 ID 기록**(중복 타격 방지)을 구현했다. 이 구조가 이후 5칸 고정 +
각인 15종 + 속성 콤보로 성숙했다.

**결과·검증**: `--cycle-test`(바늘 런타임 · 실시간 12초) · `--v4-test`(5칸 덱) 통과 +
실제 창 확인. 게임 제목이 `THE UNCHOSEN` → `딜싸이클 용사`로 바뀐 지점이 여기다.

### 5.3 프롬프트 3 — 규칙 상한과 밸런스 가드를 미리 박다 (과열 폐기)

**상황**: 각인이 바늘을 되돌려 한 바퀴가 무한히 길어지는 것을 **확률 감쇠(과열)** 로 막고
있었고, 플레이어는 왜 각인이 안 터지는지 이해할 수 없었다.

```text
[문제] 지금 "과열"은 확률로 각인을 죽인다. 플레이어가 원인을 볼 수 없으니
  이건 규칙이 아니라 노이즈다.

[지시] 과열을 상수·함수·결과 키·화면 문구까지 전부 삭제하고, 아래 한 줄로 대체해라.
   ▶ "한 칸은 한 바퀴에 두 번까지만 밟는다."

[제약]
  - 각인은 24종에서 15종으로 줄인다(칸 각인 10 + 레일 각인 5). 겹치는 개념은 합쳐라.
  - 같은 각인을 몰빵했을 때 이득이 선형으로 계속 커지면 안 된다. 사본에는 감쇠를 넣어라.
  - RELOAD는 밟은 칸 수에 선형이어야 한다. 확률 항을 다시 넣지 마라.

[증명 요구] 이 규칙에서 한 바퀴가 반드시 끝난다는 것을 확률이 아니라 산수로 증명해서
  문서에 남겨라. 칸이 5개일 때 최대 몇 스텝인지 상한을 숫자로 적어라.

[완료 판정] 각인 조합을 무작위로 수만 번 굴리는 몬테카를로 검사를 만들어
  ① 한 바퀴 상한 초과 0건 ② 한 칸 2회 초과 0건 ③ 스텝 상한 위반 0건
  을 출력으로 단언해라. 삭제한 심볼을 누가 되살리면 데이터 검사가 잡게 해라.
```

**AI가 수행한 것**: 과열 관련 **상수 15개 · 함수 4개**와 결과 키 전량을 삭제하고
`SLOT_EXEC_CAP = 2` 한 줄로 교체했다. 종료성은 **`E = Σ executed[i]`가 매 스텝 최소 1
증가하고 각 칸이 2를 못 넘으므로 `≤ 2n = 10스텝`** 으로 증명해 문서에 남겼다.
몰빵 방지는 엔진의 사본 감쇠(`DUP_MAG_FALLOFF 0.60`)로 처리했다.

**결과·검증**: `rune_test.gd` 몬테카를로 **25,001 사이클** —
`overload_count=0 exec_cap_violations=0 step_bound_violations=0`,
무작위 최대 스텝이 정확히 **10**(2n 상한이 여유 없이 딱 맞았다) · 평균 3.86스텝.

### 5.4 프롬프트 4 — "숫자를 고치기 전에 근거를 계산하는 도구를 먼저 만들어라"

**상황**: 관문·마왕 난이도를 감으로 조정하다 매 웨이브 밸런스 회귀가 반복됐다.

```text
[요구] 밸런스 상수를 감으로 바꾸지 마라.
  근거를 계산하는 도구를 먼저 만들고, 그 출력으로 바꿔라.

[만들 것] balance_probe — 게임 창을 띄우지 않고 헤드리스로 도는 밸런스 계산기.
  아래를 각각 절로 나눠 숫자로 내라.
  ① 표준 덱 한 바퀴 화력  ② 스테이지별 마물 체력 복리 지수  ③ 머문 시간(체류) 압박 곡선
  ④ 동시 물량 상한        ⑤ 골드 수지                      ⑥ 관문 보스 TTK  ⑦ 마왕 TTK

[목표 창 — 프로브가 스스로 판정해라]
  - 관문 보스 30~60초 · 마왕 60~120초
  - 한 판을 깨는 데 15~20일
  - 골드는 빠듯하되 여유 15~30%

[출력 계약] 마지막 줄에 판정 축마다 1/0을 찍고, 전부 1일 때만 `pass=1`을 찍어라.
  이 줄을 앞으로 회귀 계약으로 쓴다. 밸런스 상수를 만지는 작업은 이 줄부터 확인한다.

[주의] 프로브가 재는 덱이 실제 게임에서 도는 덱과 같은지 먼저 확인해라.
  프로브에서만 통과하는 숫자는 아무 의미가 없다.
```

**AI가 수행한 것**: 12개 절 · 판정 8축의 프로브를 작성했다. 그 과정에서 **프로브의 덱 표가
폐기된 구 각인 ID를 쓰고 있어 각인이 한 번도 주입되지 않았다**는 사실을 스스로 찾아냈다
(단서: 어느 행에서나 `steps`가 정확히 `5.00` — 흐름 각인이 0개일 때만 나오는 값이다).

**결과·검증**: 프로브 전면 재작성 후 5스테이지 표준 덱의 화력이 **119.7 → 394.3**으로
정정되고, 보스 HP·마왕 HP·체류 곡선을 전량 재측정했다. 관문 TTK 실측은
**45 / 53 / 56 / 38 / 36초**로 목표 창(30~60초) 안에 들어왔다.

```text
BALANCE_PROBE_COMPLETE pass=1 rune_steps=1 hp_index=1 dwell_curve=1
                       dwell_pressure=1 volume=1 gold=1 boss_ttk=1 demon_ttk=1
```

### 5.5 프롬프트 5 — 버그는 "고쳐라"가 아니라 "재현 → 가설 → 확정 → 재발 방지"로 시킨다

**상황**: 보물상자를 열면 **상자 위치 표시가 화면에서 사라졌다.**

```text
[증상] 보물상자를 열고 나면 그 상자의 위치 표시가 사라진다. 상자는 분명히 열렸다.
[재현] 새 게임 → 첫 상자까지 이동 → 상호작용 → 좌표 사라짐. 3회 중 3회 재현.

[순서를 지켜라 — 바로 고치지 마라]
  1. 먼저 이 증상이 나오는 최소 경로를 코드에서 찾아 나에게 말로 설명해라.
  2. 원인 가설을 둘 이상 세우고, 각각을 코드 근거로 배제하거나 확정해라.
  3. 그 다음에 고쳐라. 같은 부류의 실수가 다른 곳에도 있는지 함께 훑어서 보고해라.
  4. 마지막으로 이 버그를 다시 잡는 자동 검사를 붙여라.
     고친 줄 하나가 아니라 "상자 → 성 → 장비 배치·버리기 → 밤 전환"까지 이어지는
     흐름을 물어야 한다.

[남길 것] 왜 이 실수가 났는지 한 줄로 인수인계 문서의 「밟은 함정」에 적어라.
  다음 세션이 같은 자리에 빠지지 않는 것이 이 작업의 진짜 산출물이다.
```

**AI가 수행한 것**: 상호작용 사전을 비우는 코드가 **같은 사전을 참조하던 상자 좌표까지
함께 지우는** 참조 공유 문제로 원인을 확정했다. 상자 ID와 위치를 **먼저 값으로 복사한 뒤**
상호작용 상태를 비우도록 고쳤다.

**결과·검증**: 상자 → 성 → 장비 배치/버리기 → 밤 전환 통합 검사 통과
(현재는 `--castle-test` / `--event-test`가 승계). 같은 부류의 함정이 문서에 기록됐다.

### 5.6 프롬프트 6 — 자가 검증 체계를 AI에게 통째로 만들게 하다

**상황**: 인간이 매번 게임을 켜서 확인하면 1주 일정에서 이 볼륨이 나오지 않는다.

```text
[전제] 나는 네 작업을 매번 게임을 켜서 확인할 시간이 없다. 통과 여부는 네가 증명해라.

[규칙] 기능을 하나 만들면 그 기능을 무는 headless 검사를 같은 작업에서 함께 만든다.
  검사 없는 기능은 "완료"가 아니다.

[검사 규격]
  - 커맨드라인 플래그 하나 = 검사 하나. 끝에 `<이름>_TEST_COMPLETE` 줄을 반드시 찍는다.
  - 판정은 사람이 읽는 문장이 아니라 `키=true` / `키=false` 형태로 찍는다.
  - 전부 한 번에 도는 러너를 만들고, 아래 중 하나라도 걸리면 FAIL로 집계해라.
      ① 종료 코드 ≠ 0            ② 기대한 완료 줄이 없음
      ③ 출력에 `=false`가 있음    ④ 출력에 `SCRIPT ERROR` / `ERROR:`가 있음
  - 나는 종료 코드 하나만 본다. 0이면 전부 통과다.

[화면은 따로] 재미와 가독성은 검사로 증명할 수 없다. 실제 창을 띄워 PNG를 저장하는
  캡처 모드를 별도로 만들어라. 캡처는 PASS/FAIL 집계에 넣지 마라 — 내가 눈으로 본다.

[함정] "0개일 때 공허하게 통과하는" 단언을 만들지 마라.
  새 단언에는 음성 대조(일부러 틀린 입력)를 같이 돌려서 빨간불이 켜지는지 확인해라.
```

**AI가 수행한 것**: 러너 `run_all.sh`와 기능 검사 **16종**(월드 · 필드 생태 · 5칸 덱 ·
성/트로피 · 균열 · 스트레스 · 스모크 · 전투 · 스테이지 클럭 · 상태이상 · 사이클 런타임 ·
각인 드래프트 · 보스 3종과 마왕전 · 이어하기 · 길잡이 · 필드 사건), 시각 캡처 **15종**을
직접 설계·구현했다. 이후 "개수를 세는 단언은 0개일 때 공허하게 통과한다"는 함정을
스스로 발견해 **음성 대조**를 규칙으로 승격시켰다.

**결과·검증**: 컴파일 1 + 기능 16종 = **요약표 17행 전부 PASS**(약 135초 · 2회 연속 재현).
캡처는 **73컷 · 고유 지문 72**(중복 1쌍은 구조적 중복임을 문서로 설명).

### 5.7 프롬프트 7 — 다음 AI 세션을 위한 인수인계 문서를 산출물로 요구하다

**상황**: AI 세션은 컨텍스트가 유한해 **반드시 끊긴다.** 매번 처음부터 설명할 수는 없다.

```text
[문제] 네 세션은 곧 끝나고, 다음 세션은 아무것도 기억하지 못한 채 시작한다.
  나는 그때마다 이 프로젝트를 처음부터 설명할 생각이 없다.

[지시] 이번 웨이브를 끝내기 전에, 다음 AI가 읽을 인수인계 문서를 산출물로 써라.
  이건 부록이 아니라 코드와 동급의 산출물이다.

[반드시 들어갈 항목]
  - 사용자 요청 / 상태(completed · in_progress · blocked) / 결정한 내용
  - 변경 파일: `정확한 경로`: 무엇을 왜 바꿨는지
  - 사용자에게 보이는 변화 · 저장 데이터 호환성
  - 실행한 검증: `정확한 명령` → PASS / FAIL / 미실행 (출력 원문을 붙여라)
  - 밟은 함정: 네가 시간을 버린 지점. 다음 세션이 같은 자리에 빠지지 않도록.
  - 이 웨이브가 하지 않은 것: 범위 밖으로 밀어낸 항목
  - 다음 AI가 시작할 정확한 지점

[금지] "UI 수정함. 테스트 대충 됨. 다음에 계속." 같은 문장.
  이런 기록이 나오면 인수인계 실패로 보고 그 웨이브는 완료로 치지 않는다.

[원본 갱신] AGENTS.md의 체크포인트와 변경 로그도 같이 갱신해라.
  세션 사이의 단일 진실 원천은 그 파일 하나다.
```

**AI가 수행한 것**: 형식이 고정된 웨이브별 핸드오프 문서 **36개**를 작성했다.
대표적으로 `handoff-y5.md`의 「밟은 함정」에 *"`enemy.gd`에 남은 디버그 `print`가
`=false` 문자열을 찍으면 `run_all.sh`가 통째로 FAIL이 된다"*를 남겼다.

**결과·검증**: 30여 웨이브가 세션 교체를 건너 이어졌고, 인수인계·설계 문서 약
**21,100줄**이 남았다. 문서에 기록된 함정이 이후 세션에서 재발한 사례는 없다.

### 5.8 프롬프트 8 — 같은 코드를 **다른 모델**에게 다시 읽힌다 (Codex 교차 검증)

**상황**: 밸런스 상수·전투 판정처럼 **되돌리기 비싼 변경**을, 그 코드를 쓴 모델의 자기
검토만으로 넘기기 불안한 구간.

```text
(OpenAI Codex CLI에 전달 — 주 에이전트가 만든 diff와 검증 출력을 그대로 넘긴다)

[역할] 너는 이 변경을 처음 보는 리뷰어다. 이 코드를 쓴 것은 다른 모델이고,
  그 모델이 남긴 설명은 근거가 아니라 "주장"으로만 취급해라.
  "동의한다"가 아니라 "틀린 곳"을 찾는 것이 네 일이다.

[대상] <변경 파일 목록 + diff>
[작성자 주장] <주 에이전트가 남긴 근거 요약과 테스트 출력 원문>

[중점적으로 볼 것]
  1. 이 테스트가 정말 이 코드를 물고 있는가. 값이 0이어도 초록불이 나오지 않는가.
  2. 배율·상수가 서로 다른 두 경로에서 중복으로 곱해지는 곳은 없는가.
  3. 작성자가 "안전하다"고 단정한 근거 중, 실제로는 확인되지 않은 것은 무엇인가.

[출력 형식] 지적마다 ① 파일·줄 ② 무엇이 틀렸는지 ③ 그렇게 본 근거 ④ 확인·재현 방법.
  확신이 없으면 "의심"으로 표시해라.
[하지 말 것] 코드를 고치지 마라. 채택 여부는 내가 정하고, 수정은 주 에이전트가 한다.
```

**AI가 수행한 것**: Codex CLI가 diff와 검증 출력을 **작성자의 설명과 분리해서** 읽고
지적 목록을 냈다. 인간 디렉터가 채택 여부를 판정한 뒤, 채택된 지적만 주 에이전트에게
되돌려 수정·재검증하게 했다.

**결과·검증**: 교차 검증이 반복해서 짚은 곳은 결국 이 프로젝트가 자체적으로도
가장 크게 데인 축과 같았다 — ***"이 검사가 정말 무언가를 재고 있는가"***.
그래서 그 축은 사람의 주의력에 맡기지 않고 **규칙으로 못 박았다**:
새 단언에는 **음성 대조**(일부러 틀린 입력으로 빨간불을 확인)를 의무화하고,
각인 ID를 갈아끼울 때는 **부착 수 단언**을 함께 넣게 했다
(`AGENTS.md` 누적 함정 23·26번).

### 5.9 이미지 생성 프롬프트 — 저작권 안전선을 프롬프트 안에 박다 (실제 원문)

초기 비주얼 방향을 잡기 위해 **OpenAI 이미지 생성으로 콘셉트 시트 1장**만 만들었다.
실제로 사용한 프롬프트의 핵심 구문은 다음과 같다.

```text
original top-down 16-bit action RPG
castle, river, bridge, roaming monsters
day-to-night raid
no existing characters or logos
```

- 저장 위치: `godot-game/art/reference/the-unchosen-visual-direction.png`
- **사용 방식**: 런타임 스프라이트로 **직접 사용하지 않는다.**
  색감 · 실루엣 · 낮/밤 대비의 **방향 참고**로만 썼다.
- `original`과 `no existing characters or logos`를 프롬프트에 **명시적으로 박은 것**이
  이 프로젝트 저작권 안전 원칙의 **첫 번째 방어선**이었다.
  생성 결과를 사후에 검열하는 것보다, 생성 조건에 금지선을 넣는 쪽이 확실하다.

### 5.10 프롬프트 운용 원칙 — 이 프로젝트가 지킨 여섯 가지

| 원칙 | 실제로 준 문장 | 어디서 볼 수 있나 |
|---|---|---|
| **판정 기준을 함께 준다** | "중학생이 봐도 알 수 있게", "한 페이지를 3초 안에 훑을 수 있게" | §3.3 · 프롬프트 6 |
| **금지선을 함께 준다** | "장르를 바꾸지 마라", "기존 작품의 인물·로고를 복제하지 않는다" | 프롬프트 1 · §5.9 |
| **상한과 가드를 미리 준다** | "한 칸은 한 바퀴에 두 번까지", "몰빵하면 감쇠가 걸리게" | 프롬프트 3 |
| **검증 방법까지 요구한다** | "확률이 아니라 산수로 증명해라", "0개여도 통과하는 단언을 만들지 마라" | 프롬프트 3 · 4 · 6 |
| **다음 세션을 위한 기록을 요구한다** | "밟은 함정과 다음 AI가 시작할 정확한 지점을 남겨라" | 프롬프트 7 |
| **다른 모델에게 다시 읽힌다** | "이 코드를 쓴 모델의 설명은 근거가 아니라 주장으로 취급해라" | 프롬프트 8 |

> 이 여섯 가지를 지키면 AI에게 "다시 해 봐"라고 말할 일이 거의 없어진다.
> **재작업을 줄인 것은 모델의 성능이 아니라 프롬프트에 미리 넣어 둔 판정 기준이었다.**

## 6. AI 산출물 검증 체계

> **구조: AI가 코드를 쓰고 → AI가 그 코드를 무는 테스트를 쓰고 →
> AI가 테스트를 돌려 결과를 제출하고 → 인간이 화면과 숫자로 최종 승인한다.**
> 되돌리기 비싼 구간은 그 사이에 **다른 모델(Codex CLI)의 리뷰 한 단계**를 더 끼웠다.

### 6.1 명령과 통과 기준

| 명령 | 무엇을 보는가 | 통과 기준 | 소요 |
|---|---|---|---|
| `bash godot-game/scripts/test/run_all.sh` | 컴파일 1 + **기능 검사 16종** | **종료 코드 0** · 요약표 17행 전부 PASS | 약 135초 |
| `run_all.sh --captures` | **시각 캡처 15종 73컷** (창을 띄움) | PNG 저장 후 **사람 눈 검수** | — |
| `balance_probe.gd` | 화력·HP 복리·체류 곡선·물량·경제·보스/마왕 TTK (12절) | 마지막 줄 **`pass=1`** (판정 8축 전부 1) | 약 90초 |
| `rune_test.gd` | 각인 15종 · 사이클 종료성 몬테카를로 | `RUNE_TEST_COMPLETE` · 전 플래그 true | — |
| `data_test.gd` | 데이터 계약(카드·아이템·몬스터·각인 정합성) | `DATA_TEST_COMPLETE` · 전 플래그 true | — |
| `rift_probe.gd` | 균열 배치 · 시드 100개 강건성 | `failures=0 verdict=PASS` | — |
| `terrain_probe.gd -- fast` | 물 비율 · 2×2 블록 통행 불변식 | `verdict=PASS block_invariant=true` | 약 40초 |

### 6.2 FAIL 판정 규칙 (기계가 판정한다)

하나라도 걸리면 그 검사는 FAIL이다.

| # | 조건 | 뜻 |
|---|---|---|
| ① | Godot 종료 코드 ≠ 0 | 테스트가 스스로 실패를 선언 |
| ② | 기대한 `*_TEST_COMPLETE` 줄이 없음 | 도중에 죽었거나 타임아웃 |
| ③ | 출력에 `=false`가 있음 | 검사 플래그 중 하나가 거짓 |
| ④ | 출력에 `SCRIPT ERROR` / `ERROR:` | 종료 코드가 0이어도 실패로 본다 |

### 6.3 실제 검증 로그 (최종 밸런스 웨이브 Y8)

```text
BALANCE_PROBE_COMPLETE pass=1 rune_steps=1 hp_index=1 dwell_curve=1
                       dwell_pressure=1 volume=1 gold=1 boss_ttk=1 demon_ttk=1
STAGE  curve=true reward_decay=true eff4=0.772 eff8=0.611 eff12=0.500 night_cap=62
CYCLE  exec_cap=true overload_hits=0 max_steps=10 max_exec=2 debt=2.42
STRESS fps=145 enemies=103 surge_peak=59 surge_cap=78
BOSS   stage_reload=1.485 expected_reload=1.485 demon_reload=0.873
DATA   rune_exec_cap=true slot_exec_cap=2 step_cap=12 runes=15
RUNE   no_overload=true overload_count=0 guard_count=0 cycles=25001
```

- `run_all.sh` **17행 전부 PASS · 2회 연속 재현**
- 몬스터 **103마리 동시 유지 상태에서 145 FPS** (성능 회귀 검사)
- 각인 사이클 **25,001회 몬테카를로에서 상한 초과 0건**

### 6.4 작업 종료 전 체크리스트 (`AGENTS.md` §13에 규정)

AI 세션은 작업을 끝내기 전에 이 절차를 반드시 통과해야 한다.

1. `run_all.sh` 전체 PASS (**17/17**)
2. 화면을 건드렸으면 캡처 육안 검수 — 찍기 전 잔여 Godot 인스턴스 0 확인,
   찍은 뒤 `shasum`으로 컷이 서로 다른지 확인
3. 저장 스키마를 건드렸으면 `--save-test` 필수 (`mismatch=0`)
4. 밸런스를 건드렸으면 `balance_probe` 재실행 — **`pass=1`** 확인 + 표를 주석에 남긴다
5. 상시 문장을 늘렸으면 글자 수 상한 계약 지표 확인
6. `AGENTS.md` 체크포인트 · 변경 로그 갱신
7. 사용자에게 무엇이 바뀌었는지 한국어로 보고

> **인간의 최종 승인 없이는 어떤 웨이브도 "완료"가 되지 않는다.**
> 자동 검사는 "AI가 인간의 시간을 낭비하지 않을 자격"을 증명하는 절차였다.

## 8. 정리

### 8.1 AI 활용의 효과 — 1주 만에 이 볼륨

| 지표 | 값 |
|---|---|
| 개발 기간 | **7일** (2026-08-03 ~ 2026-08-10) |
| GDScript | 46개 파일 · 약 **48,900줄** |
| 인수인계·설계 문서 | 36개 핸드오프 + 설계 문서 · 약 **21,100줄** |
| 자동 검사 | 컴파일 1 + 기능 16종 + 프로브 5종 + 시각 캡처 15종 73컷 |
| 콘텐츠 | 스킬 카드 28종 · 장비 57종 · 각인 15종 · 몬스터 10종 · 보스 3종 + 마왕 · 필드 사건 8종 · 소비 아이템 8종 · 5스테이지 |
| 개발 라운드 | W(v2) → V(v3) → U(UI) → X(1차 피드백) → Y(2차 피드백 25건) — **총 30여 웨이브** |

이 규모가 나온 이유는 코드 생성 속도 때문이 아니라,
**"AI가 자기 작업을 스스로 검증하고, 다음 AI에게 정확히 인계하는 구조"**를
초반에 세워 뒀기 때문이다. 인간의 검토 시간이 병목이 되지 않았다.
되돌리기 비싼 구간에만 **다른 모델(Codex CLI)의 리뷰**를 한 겹 더 얹어,
"한 모델이 자기 실수를 자기 눈으로 찾아야 하는" 상황을 줄였다.

### 8.2 인간 디렉팅이 결정적이었던 지점

AI가 스스로 도달하지 못했고, **인간의 한 문장이 프로젝트 전체를 바꾼** 지점은 넷이다.

1. **정체성** — *"고르지 않은 선택이 마왕에게 돌아온다."*
   AI는 이 축이 없을 때 장르 자체를(벽돌깨기로) 바꿔 버렸다.
2. **중심 규칙 교체** — *"동시 발동을 폐기하고 레일로 바꿔라."*
   플레이어가 자기 행동을 볼 수 있게 된 순간이다.
3. **복잡도 제거** — *"과열을 없애라", "블록을 다 지워라", "텍스트를 반으로."*
   AI는 기능을 **더하는 쪽**으로는 잘 가지만, **덜어내는 판단**은 인간이 내렸다.
4. **재미의 판정** — *"검사는 통과했는데 어렵지가 않다 / 안 읽힌다."*
   headless 검사는 무너짐만 잡는다. 재미·가독성·난이도는 실제 창에서만 판정됐다.

### 8.3 이 프로젝트가 제안하는 AI 활용 방법론 3줄

> ① **세션은 끊긴다 — 인계 문서를 산출물로 취급한다.**
> ② **AI가 만든 것은 AI가 만든 검사로 잡되, 그 검사가 무엇을 재는지 인간이 의심한다.**
> ③ **감각적 요구("가린다", "복잡하다")를 숫자 계약으로 번역하면 회귀가 자동으로 잡힌다.**
